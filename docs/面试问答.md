# 面试问答手册

> 用法：不要背全文，背“骨架”和“取舍”。每个问题先说结论，再说为什么，最后主动补一句不足，面试官会觉得你想过。

## 一、项目介绍（1 分钟版）

> 这是一个演出票务平台，核心是抢票链路。用户浏览场馆和演出，开票时抢票；抢票接口只用 Redis + Lua 做原子校验和库存预扣，订单通过 RabbitMQ 异步落库；未支付订单通过 TTL + 死信队列的延迟消息自动取消并回补库存。配套做了登录鉴权与发送限流、场馆缓存、剧评点赞和关注流，前端是 Vue3 + nginx 反代。

**3 分钟版补充**：数据规模（12 场馆 / 22 演出 / 10 用户种子数据）、实测结果（30ms 落库、60 秒自动关单、库存回补）、已知不足（没开 publisher confirm、没做压测）。

## 二、抢票链路

**1. 怎么防超卖？**
Redis 预扣是第一道闸门，DB 乐观锁 `stock = stock - 1 where stock > 0` 是最终保证。Redis 挡掉绝大部分请求，DB 保证即使 Redis 数据异常也不会卖超。

**2. 怎么保证一人一票？**
Redis Set 存已购用户，Lua 里 `SISMEMBER` 判断 + `SADD` 占位与扣库存原子完成。取消订单时 `SREM` 释放，允许重新购买。

**3. 为什么用 Lua，不用分布式锁？**
Lua 在 Redis 单线程内一次执行完“判断库存 + 判断限购 + 扣减”，零并发窗口、一次网络往返。分布式锁要把每个请求串行化，RT 和吞吐都差，还有锁超时、误删、续期问题。

**4. Redis 库存和 DB 库存怎么一致？**
Redis 只做准入（预扣），DB 是最终依据。消费者落库时再扣一次 DB 库存；DB 扣失败说明不一致，回补 Redis 并告警。取消订单时两边都加回去。

**5. Redis 挂了怎么办？**
当前直接失败（快速失败好过超卖）。可以说出降级方案：DB 乐观锁兜底 + 入口限流保护数据库。

**6. 接口瓶颈在哪？**
瓶颈在 Redis 单线程和网络往返（一次 Lua），不在 DB。再往上要加本地缓存/分片，但本项目数据量没到。

## 三、消息队列

**7. 为什么要用 MQ？**
抢票接口只做 Redis 操作，落库异步化，接口 RT 从“等 DB 事务”变成“一次 Redis + 一次发送”，数据库连接和行锁竞争与接口流量解耦。

**8. 为什么选 RabbitMQ 不选 RocketMQ/Kafka？**
RabbitMQ 资源占用小、路由灵活，TTL + 死信就能实现延迟关单；RocketMQ 默认 4G 堆对本地开发太重；Kafka 偏流处理，延迟消息要自己做。选型依据是场景规模，不是谁更“高级”。

**9. 为什么不用 Redis Stream（课程原方案）？**
Stream 能做消息队列，但消费重试、死信、堆积监控都要自己维护 pending-list，等于手写 MQ。

**10. 消息重复消费怎么办？**
RabbitMQ 是 at-least-once。订单号在入口生成随消息传递，消费端先按订单号查重；扣库存和插订单同事务，主键冲突会回滚。

**11. 消息丢失怎么办？**
当前只保证同步发送 + 消费端异常重试；**没有开 publisher confirm**，极端情况可能丢。改进：publisher confirm + return，或者本地消息表/事务性 outbox。

**12. 延迟关单怎么实现的？**
消息投到无消费者的 `ticket.delay.queue`，队列级 TTL 到期后成为死信，按 DLX 路由到 `ticket.timeout.queue`；消费者检查订单，未支付则条件更新为已取消并回补三处库存。

**13. 为什么不用定时任务扫表？**
扫表有固定周期延迟（分钟级），订单量大时全表扫描压力大，还可能和大促流量叠加；延迟消息更精确、更省资源。

**14. TTL 队列有什么坑？**
TTL 是队列级参数，改了要先删队列再重启；同一队列消息按队头过期，差异化延迟不适合一个队列（需要每档一个队列）。

**15. 消费失败怎么办？**
本地重试 3 次指数退避，耗尽后 `default-requeue-rejected: false` 进入死信交换机，最终到 `ticket.dead.queue`，可人工补偿。不能无限重回队列，会打满 CPU。

**16. 支付和关单并发怎么办？**
都改成 `UPDATE ... WHERE status = 1` 条件更新，看影响行数；只有关单成功那次才回补库存。

## 四、缓存

**17. 缓存穿透、击穿、雪崩分别是什么，你怎么解决？**
- 穿透（查不存在的数据）：空值缓存 2 分钟，防同一无效 key 反复打库
- 击穿（热点 key 过期）：逻辑过期 + 抢锁异步重建，请求永远拿得到数据
- 雪崩（大量 key 同时过期）：物理不设 TTL / TTL 加随机

**18. 逻辑过期怎么做？**
value 包 `{data, expireTime}`，读取时比较过期时间；过期则 `SETNX` 抢重建锁，抢到丢线程池，没抢到返回旧值。

**19. 逻辑过期和互斥锁怎么选？**
互斥锁保证强一致但会阻塞；逻辑过期保证可用性，允许短暂脏读。场馆详情允许旧值，选逻辑过期；订单/库存不能容忍旧值，就不走缓存。

**20. 缓存和数据库一致性怎么保证？**
Cache Aside：先更新 DB 再删缓存。仍有极小窗口不一致，生产可用延迟双删或 binlog 订阅补偿。

**21. 为什么不用本地缓存（Caffeine）？**
单机缓存多实例不一致，且本项目热点是场馆详情，Redis + 逻辑过期已够；本地缓存适合极端热点，可做多级缓存的下一步优化。

## 五、鉴权

**22. 登录怎么实现的？**
验证码存 Redis（2 分钟），登录后生成 UUID token，用户信息 Hash 存 Redis（30 分钟滑动续期）；两个拦截器：一个负责解析 token 和续期（所有请求），一个负责校验登录态（非白名单）。

**23. 为什么不用 JWT？**
JWT 无法主动失效（登出、踢人、封号要等过期），续期要双 token；本项目有集中 Redis，有状态 token 更好控制。取舍是 Redis 故障时登录态全失效。

**24. 验证码怎么防刷？**
手机号 60 秒冷却 + IP 每小时 10 次，Lua 原子；连续输错 5 次锁定 15 分钟。两个维度分别防“换号刷”和“单号刷”。

**25. 怎么强制下线？**
删 `show-ticket:login:token:{token}` 即 401。要踢该用户所有设备，需要维护 userId → token 集合（未做）。

**26. 为什么不用 Spring Security？**
当前需求是登录态 + 少量白名单，拦截器足够；Spring Security 学习成本高、配置复杂，引入后要重写过滤器链。后续做 RBAC 再评估。

## 六、数据库与事务

**27. 订单表怎么设计的？**
主键是业务生成的订单号（非自增），`user_id`、`show_id`、`status`、时间字段；索引 `idx_user_id`、`idx_show_id`、`idx_status_create`（关单扫描/后台查询用）。

**28. 为什么不建 (user_id, show_id) 唯一索引？**
取消订单后要允许重新购买，唯一索引会挡住；一人一票由 Redis Set 控制，取消时释放。这是刻意取舍。

**29. 事务边界怎么划的？**
`createTicketOrder` 内“扣库存 + 插订单”同一事务，任一步失败回滚；Redis 不参与事务，补偿逻辑显式写在异常分支。

**30. 乐观锁和悲观锁怎么选？**
秒杀热点行写冲突高，悲观锁（`select for update`）会排队；乐观锁失败重试成本低，配合 Redis 预扣后 DB 冲突已经很少。

**31. 消息消费的方法上 @Transactional 会生效吗？**
会，消费者是外部调用（跨 bean），走代理。曾经的坑是同类内部自调用导致事务失效。

## 七、全局 ID

**32. 订单号怎么生成的？**
`(当前秒 - 2022-01-01) << 32 | Redis 当日自增`，按天分 key。单调递增，写入 MySQL 顺序插入，减少页分裂。

**33. 为什么不用 UUID / 数据库自增 / 雪花？**
UUID 无序且索引大；数据库自增暴露订单量、分库麻烦；雪花要管理 workerId 和时钟回拨。已有 Redis，复用成本最低。

## 八、压测与优化（诚实回答）

**34. 你压测了吗？数据呢？**
目前还没做 JMeter 压测（计划中），但已验证正确性：500 并发抢 50 张票不超卖、重复下单被拒、60 秒自动关单、库存回补。压测会对比“同步落库”和“MQ 异步”两种实现的 QPS/P99。

**35. 流量涨 10 倍，瓶颈在哪，怎么优化？**
瓶颈顺序：单机 Redis 网络 → 应用 CPU/线程 → MQ 消费能力 → DB 写入。优化：应用无状态扩容、Redis 集群/读写分离、MQ 增加消费者、DB 分库分表；入口加限流和降级，非核心接口熔断。

**36. 你项目里最难的三个点？**
1. Redis 预扣与 DB 最终一致（回补、幂等、并发条件更新）
2. 延迟关单的可靠性与并发状态机
3. 让“抢票成功但订单还没落库”这个时间窗口对用户无感（返回订单号 + 轮询查询）
