# 缓存设计：穿透、击穿与一致性

> 简历一句话：场馆详情采用逻辑过期 + 互斥重建防击穿、空值缓存防穿透，启动预热 + 更新后删缓存保证一致性。

## 1. 三类缓存问题

| 问题 | 场景 | 本项目方案 |
| --- | --- | --- |
| 穿透 | 查不存在的数据，请求全打到 DB | 空值缓存（`""`，短 TTL） |
| 击穿 | 热点 key 过期瞬间大量请求同时重建 | 逻辑过期：value 里带过期时间，异步线程重建，旧值兜底 |
| 雪崩 | 大量 key 同时过期 | TTL 加随机值；本项目场馆数据用预热 + 逻辑过期，不设物理 TTL |

## 2. 实现位置

- `utils/CacheClient.java`
  - `queryWithPassThrough`：查缓存 → 空值直接返回 → 查 DB → 不存在写 `""` → 存在写 JSON
  - `queryWithLogicalExpire`：查缓存 → 未逻辑过期直接返回 → 过期则抢锁，抢到的线程丢线程池重建，没抢到的返回旧值
- `service/impl/VenueServiceImpl.java`：`queryById` 走逻辑过期；`updateVenue` 先更新 DB 再删缓存
- `config/WarmupRunner.java`：启动时把所有场馆写入逻辑过期缓存

## 3. 为什么用逻辑过期

互斥锁方案会在重建期间阻塞请求，热点 key 过期瞬间接口 RT 飙升；逻辑过期保证所有请求都能立刻拿到数据（可能是旧值），只有后台线程去重建。

代价是**短暂脏读**：数据更新后，缓存要等下一次重建才刷新。本项目通过「更新 DB 后主动删缓存」规避。

## 4. 一致性策略

采用 **Cache Aside**：先更新数据库，再删除缓存。

- 为什么不是「更新缓存」：并发更新时可能用旧值覆盖新值，且缓存内容可能由多个表拼装，更新成本高。
- 为什么不是「先删缓存再更 DB」：删除后到更新前的窗口内，读请求会把旧值重新写回缓存，脏数据停留更久。
- 更新后立刻删缓存仍有极小概率不一致（读请求在删除前拿到旧值并写回），生产可用延迟双删或订阅 binlog（Canal）补偿，本项目未做。

## 5. 踩过的坑

1. **逻辑过期缓存没预热时会返回 null**：key 不存在时 `queryWithLogicalExpire` 直接返回 null，页面提示“场馆不存在”。修复方式是启动预热（`WarmupRunner`），新数据写入后也依赖重启预热或访问时懒加载。
2. **空值缓存不能设太长**：TTL 2 分钟，避免数据补录后长时间查不到。
3. **缓存 key 要带业务前缀**：多项目共用 Redis，统一 `show-ticket:` 前缀，否则 `cache:venue:` 这种 key 很容易和别的项目撞。

## 6. 面试追问

- Q：逻辑过期怎么实现？→ value 包一层 `{data, expireTime}`，取出来先看 `expireTime`，过期就尝试 `SETNX` 抢重建锁，抢到丢线程池重建，没抢到返回旧数据。
- Q：缓存和数据库不一致怎么办？→ 先更 DB 再删缓存，接受极小窗口；强一致要上分布式事务或 binlog 同步，成本和收益不匹配。
- Q：为什么不用布隆过滤器防穿透？→ 数据量小、空值缓存足够；布隆过滤器有误判和删除麻烦的问题，适合大数据量场景。
- Q：热点 key 怎么发现？→ 生产可用 Redis 的 hotkey 监控或本地缓存计数；本项目场馆详情就是典型热点 key，所以直接上逻辑过期。
