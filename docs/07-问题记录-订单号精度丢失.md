# 问题记录：订单号精度丢失导致支付失败

> 级别：P0（核心支付链路不可用）｜状态：已修复（`bdeada8`）｜发现场景：前端点击「立即支付」

## 1. 问题是什么

**现象**：订单列表能看到订单，点击「支付」提示「订单不存在」。

**影响范围**：所有依赖订单号的接口——支付、订单详情、订单列表前端展示；抢票成功后返回的订单号同样不可信。

**严重程度**：支付链路完全不可用，用户抢到票但无法支付，且 60 秒后订单会被自动取消，等于抢票功能整体失效。

## 2. 如何复现（修复前）

1. 抢票成功，拿到订单号（形如 `653386116245749764`）
2. 打开「我的订单」，能看到这条订单
3. 点「立即支付」→ 后端返回 `{"success":false,"errorMsg":"订单不存在"}`
4. 用 curl 传**精确的原始 ID** 查询 → 能查到；传列表接口返回的 ID → 查不到

## 3. 根因

订单号由 Redis 全局 ID 生成器产生：`(秒级时间戳 - 2022-01-01) << 32 | 当日自增`，长度 18 位（约 6.5×10¹⁷）。

JavaScript 的 Number 是 IEEE 754 双精度浮点，能精确表示的整数上限是 `Number.MAX_SAFE_INTEGER = 9007199254740991`（约 9×10¹⁵，16 位）。18 位整数超出后，末几位被四舍五入：

```
后端返回的 JSON: {"id":653386116245749764}
浏览器 JSON.parse:  653386116245749800     ← 末两位被改写，差 36
```

前端列表展示、支付拼接 URL 用的都是这个被截断的值，后端按错误的 ID 查库返回 null，于是提示「订单不存在」。

**用 Node 复现（和浏览器同引擎）**：

```bash
node -e "const s='653386116245749764';
console.log(String(JSON.parse('{\"id\":'+s+'}').id) === s)"   # 输出 false
```

## 4. 为什么列表里能看到订单

订单列表是后端按 `user_id` 查询的，和订单号无关，所以列表正常；支付是按订单号精确查询，被截断后就查不到了。这也是排查时容易误判为“订单没落库”的地方。

## 5. 修复方案

**改动 1**：`entity/TicketOrder.java` 的 `id` 字段加注解，序列化成字符串

```java
@JsonSerialize(using = ToStringSerializer.class)
@TableId(value = "id", type = IdType.INPUT)
private Long id;
```

**改动 2**：`TicketOrderServiceImpl.grabTicket` 返回字符串订单号

```java
return Result.ok(orderId.toString());
```

**前端无需改动**：订单号作为不透明标识直接拼 URL，字符串不受精度影响。

## 6. 验证

- Jackson 序列化实测：`{"id":"653386116245749764",...}`，`id` 为字符串（已通过）
- 接口级验证（抢票 → 列表取字符串 ID → 支付成功）待 Redis/MQ 环境启动后补测

## 7. 备选方案与取舍

| 方案 | 优点 | 不选的原因 |
| --- | --- | --- |
| **字段级 `ToStringSerializer`（选用）** | 影响面最小，只改订单号 | 新增超大 ID 字段时需要记得同样处理 |
| 全局 Long → String | 一次配置永久生效 | 价格、销量、积分等全变字符串，前端算术依赖隐式转换，契约变化大 |
| 前端用 `json-bigint` 解析 | 不改后端 | 每个请求都要换解析器，团队协作成本高，依然要约定哪些字段是大整数 |
| 订单号压缩到 53 bit 内 | 前端零改造 | 时间戳 + 序列号位数不够，容量和可读性都下降，且未来仍可能越界 |
| 订单号直接用字符串类型存储 | 前后端天然一致 | 数据库索引体积变大，且现有 ID 生成器返回 long，改动面大 |

## 8. 如何预防

1. 约定：**任何可能超过 2⁵³ 的 ID 对外一律序列化为字符串**（订单号、雪花 ID、分布式 ID 都适用）
2. 接口测试加断言：`/ticket-order/{id}` 返回的 `id` 必须是 JSON 字符串
3. 前端把 ID 当不透明字符串处理，禁止 `Number(id)`、`parseInt(id)`

## 9. 面试怎么讲

> 我的订单号是 18 位分布式 ID，超过 JS 安全整数范围，前端 JSON 解析会丢精度，列表里能看到订单但支付时拿错误 ID 查不到。定位方法是拿精确 ID 用 curl 验证接口本身正常，确认是前端解析问题。修复是订单号以字符串返回，前端作为不透明标识使用；没有全局改 Long，是因为价格等字段还要参与计算，定点处理影响面最小。
