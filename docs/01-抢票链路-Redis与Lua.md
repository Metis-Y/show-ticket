# 抢票链路：Redis + Lua 原子预扣

> 简历一句话：基于 Redis + Lua 实现抢票资格原子校验与库存预扣，订单经 RabbitMQ 异步落库，接口全程不访问数据库。

## 1. 业务场景

演出开票瞬间，几百上千人同时抢同一场有限库存（种子数据里热门场次只有 60~80 张票）。

## 2. 要解决的问题

| 问题 | 后果 |
| --- | --- |
| 超卖 | 卖出去的票比库存多，资损 |
| 一人多单 | 黄牛刷票，普通用户抢不到 |
| 接口 RT 高 | 每个请求都查库扣库，行锁排队，响应从毫秒级涨到秒级 |
| DB 被打满 | 瞬时流量直接打到 MySQL，连接池耗尽，影响其他接口 |

## 3. 方案

```
请求 → Redis(Lua 原子校验+预扣) → 成功 → 发 MQ → 立即返回订单号
                                      ↓
                              消费者异步落库（扣 DB 库存 + 插订单）
```

### 3.1 预热

`WarmupRunner` 启动时把三类数据写进 Redis：

- `show-ticket:ticket:stock:{showId}`：剩余票数（String）
- `show-ticket:ticket:window:{showId}`：开售/停售时间（Hash，存 epoch 秒）
- `show-ticket:ticket:order:{showId}`：已抢到票的用户集合（Set）

Redis 数据被清空也不怕：Lua 返回 5（未预热）时，`grabTicket` 会调用 `warmUp(showId)` 从 DB 懒加载后重试一次。

### 3.2 Lua 原子校验

`backend/src/main/resources/grab.lua`：

```lua
-- ARGV[1] 前缀, ARGV[2] showId, ARGV[3] userId, ARGV[4] 当前 epoch 秒
1. 库存 key 不存在        → 返回 5（未预热）
2. 当前时间 < 开售时间     → 返回 3
3. 当前时间 > 停售时间     → 返回 4
4. 库存 <= 0              → 返回 1
5. 用户在限购集合里        → 返回 2
6. 扣库存 + 写入限购集合   → 返回 0
```

整段在 Redis 单线程内执行，判断和扣减之间没有并发窗口。

### 3.3 异步落库

Lua 返回 0 后，`TicketOrderServiceImpl.grabTicket` 只做两件事：发下单消息、发延迟关单消息，然后立即返回订单号。DB 写入全部由消费者完成。

### 3.4 失败补偿

- **MQ 发送失败**（broker 不可用）：立即 `INCR` 回补 Redis 库存、`SREM` 释放限购占位，返回「系统繁忙」，避免“扣了票却没有订单”。
- **DB 库存不足**（Redis 与 DB 不一致）：消费者回补 Redis 占位并告警，消息正常 ack，不做无意义重试。

## 4. 为什么这么选

| 决策 | 原因 | 不选的方案及原因 |
| --- | --- | --- |
| Lua 原子校验 | 单次网络往返，Redis 单线程保证原子性，吞吐最高 | 分布式锁：每个请求都要加锁释放，秒杀场景下等于把并发串行化，RT 和吞吐都差；还有锁超时、误删等问题 |
| Redis 预扣库存 | 库存判断是热点写，放 DB 会行锁排队 | 数据库乐观锁：热点行 UPDATE 冲突率高，重试多；悲观锁：直接串行化 |
| 开售窗口也放 Redis | 避免每次请求查库判断时间 | 每次查 DB：多一次 RT，且 Redis 已有库存数据，顺路校验最便宜 |
| 用 Hash 存时间 | 一个 key 存 begin/end，Lua 里两次 HGET 即可 | 两个独立 String key：多一次 key 查询，且容易漏设 TTL |
| 入口生成订单号 | 订单号随消息传递，消费端可用它做幂等 | 消费端生成：消息重投会生成两个订单号，幂等无从谈起 |

## 5. 踩过的坑

1. **Lua 里的 key 前缀必须和 Java 一致**：最初前缀写死在 Lua 里，后来给所有 Redis key 加 `show-ticket:` 前缀时改成由 Java 通过 `ARGV[1]` 传入，保证只有一处定义。
2. **取消订单后要释放限购占位**：只回补库存、不 `SREM`，用户会被永久挡在“请勿重复下单”外。
3. **未预热时不能直接判售罄**：最初库存 key 不存在时 `tonumber(nil)` 比较会抛错/误判，改成显式返回 5 并触发懒加载。
4. **Redis 和 DB 库存要双向回补**：只补一边，下一次抢票就会因为两边不一致出现“有票却下单失败”。

## 6. 实测

- 抢票成功到订单落库：30ms（`17:51:50.4` 返回订单号，`17:51:50.512` 落库完成）
- 同一用户第二次抢：`每人限购一张，请勿重复下单`
- 库存 0 的场次：`票已售罄`
- 未开售场次：`还未开票，请稍后再来`
- MQ 不可用时：返回「系统繁忙」，Redis 库存从 49 回补到 50

## 7. 面试追问

- Q：Lua 脚本执行期间 Redis 会阻塞吗？脚本太复杂会不会影响其他请求？→ 会阻塞，Redis 单线程；所以脚本只做 O(1) 的读写，不做循环和复杂计算。
- Q：Redis 挂了怎么办？→ 当前没有降级方案，抢票直接失败（快速失败比超卖好）；生产可降级为 DB 乐观锁兜底，或者用本地限流保护 DB。
- Q：库存和订单的一致性怎么保证？→ Redis 只是预扣（准入），DB 才是最终依据；消费者用乐观锁再扣一次，失败说明不一致，回补 Redis 并告警。
- Q：为什么不用 Redis 的 DECR 直接判断？→ DECR 无法同时完成“限购判断 + 扣减”这一组操作，Lua 才能保证组合操作原子。
