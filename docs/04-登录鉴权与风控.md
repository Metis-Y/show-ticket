# 登录鉴权与风控

> 简历一句话：Redis 有状态 Token + 双拦截器实现无感续期；验证码发送限流（手机号 + IP 双维度）与失败锁定防刷防爆破。

## 1. 登录流程

```
POST /user/code?phone=xxx
  → 校验手机号格式
  → 限流（手机号 60s 冷却 + IP 每小时 10 次，Lua 原子）
  → 生成 6 位验证码，写入 Redis（TTL 2 分钟），控制台打印（模拟短信）
POST /user/login {phone, code}
  → 校验失败次数是否已达 5 次（锁定 15 分钟）
  → 比对 Redis 中的验证码
  → 查询/创建用户
  → 生成 UUID token，用户信息以 Hash 写入 Redis，TTL 30 分钟
  → 返回 token，前端存 localStorage，后续请求放 authorization 头
```

## 2. 双拦截器

| 拦截器 | order | 作用 |
| --- | --- | --- |
| `RefreshTokenInterceptor` | 0 | 所有请求：解析 authorization，从 Redis 取用户 Hash，刷新 TTL（滑动续期），写入 `UserHolder`（ThreadLocal） |
| `LoginInterceptor` | 1 | 非白名单请求：`UserHolder` 为空则返回 401；请求结束清理 ThreadLocal |

为什么拆两个：刷新逻辑需要覆盖所有请求（包括公开接口，保证已登录用户访问公开页也续期），而登录校验只需要拦需要登录的接口。

## 3. 为什么不用 JWT

| 维度 | JWT（无状态） | Redis Token（本项目） |
| --- | --- | --- |
| 主动失效 | 难，签发后到期前都有效，除非维护黑名单 | 直接删 key，登出/踢人/封号立即生效 |
| 续期 | 需要双 token（access + refresh）或每次重签 | 每次请求 `EXPIRE` 一行代码 |
| 权限变更 | 要等 token 过期或加黑名单 | 改 Redis 里的用户信息即可 |
| 服务端存储 | 无 | 每个登录用户一个 Hash（内存成本可控） |
| 适用场景 | 多服务无共享存储、开放 API | 单体/有集中 Redis 的业务系统 |

结论：本项目是单体 + 已有 Redis，**会话可控性比无状态更重要**，所以选有状态 Token。面试时不要只说“JWT 不安全”，要讲清楚取舍。

## 4. 风控设计

### 4.1 验证码发送限流

- 同一手机号 60 秒一次（`show-ticket:login:code:cooldown:{phone}`）
- 同一 IP 每小时最多 10 次（`show-ticket:login:code:ip:{ip}`）
- 两个判断 + 两个写入放在一个 Lua 脚本里原子执行（`send_code_limit.lua`）

**为什么两个维度都要**：只限手机号，换个号码就能继续刷；只限 IP，NAT 后的正常用户会被误伤。

**为什么用 Lua**：`EXISTS` + `INCR` + `EXPIRE` 分开执行，并发下会超发（两个请求同时通过检查）。

### 4.2 登录失败锁定

- 连续输错 5 次 → 锁定 15 分钟（`show-ticket:login:fail:{phone}`）
- 每次失败 `INCR`，首次失败设置 TTL；登录成功 `DEL`
- 锁定时返回剩余分钟数

### 4.3 为什么不用现成的限流组件

| 方案 | 不用的原因 |
| --- | --- |
| Guava RateLimiter | 单机内存计数，多实例部署时每个实例独立，限制会放大 N 倍 |
| Sentinel | 功能重，适合接口级 QPS 限流；本项目还需要“按手机号”这种业务维度，用 Redis 更直接 |
| nginx limit_req | 只能按 IP 粗粒度限流，拿不到业务参数（手机号） |
| Spring Session + 拦截器 | 没有现成的发送间隔控制，还是要自己写计数 |

## 5. 踩过的坑

1. **客户端 IP 取错**：经过 nginx 反代后 `getRemoteAddr()` 拿到的是 127.0.0.1，所有用户共享一个 IP 配额。修复：优先取 `X-Real-IP`，其次 `X-Forwarded-For`，最后 `getRemoteAddr()`。
2. **修改接口签名影响调用方**：`sendCode` 从 `(phone, session)` 改成 `(phone, clientIp)`，需要同步改 Controller 和接口定义。
3. **锁定期不该继续累加失败次数**：锁定后直接返回，避免用户等待期间计数继续增长导致时间被无限延长。

## 6. 已知不足 / 待做

- `logout()` 仍是 TODO（直接删 Redis token 即可实现）
- 没有单点登录互踢（同一账号新登录使旧 token 失效）
- token 未绑定设备信息，无法识别异地登录
- 未强制 HTTPS，token 明文传输只适用于本地开发

## 7. 面试追问

- Q：token 为什么放 header 不放 cookie？→ 避免 CSRF；前后端分离跨域时 cookie 需要 SameSite/凭证配置，header 更简单。
- Q：token 过期了用户正在操作怎么办？→ 滑动续期：每次请求刷新 TTL，只要活跃就不会过期；完全不活跃超过 30 分钟才需要重新登录。
- Q：如何强制某个用户下线？→ 删除 `login:token:{token}`，下次请求 401；如果要做“该用户所有设备下线”，需要维护 userId → token 集合，目前未做。
- Q：Redis 挂了登录态怎么办？→ 所有请求 401，用户重新登录；这是有状态会话的代价，换取的是可控性。
- Q：验证码为什么存 Redis 不存 session？→ 支持多实例部署；session 需要额外的共享存储方案。
