# 08 退票功能设计

> 状态：设计说明（待实施）。本文是「AI 票务助手」售后闭环的执行动作，由 ShowTicket 后端实现。
> 实施者注意：只实现退票链路，**不改动抢票 / 支付 / 超时关单的现有行为**；遵循现有代码风格（`Result` 包装、`UserHolder` 取当前用户、MyBatis-Plus 条件更新、日志前缀 `[退款]`）。

## 1. 背景与目标

AI 票务助手的售后闭环需要一个真实可执行的退票动作：用户用自然语言申请退票 → AI 依据规则判定（试算）→ 调用本接口真正退票 → 订单状态、库存、限购占位完整回补。

v1 目标：**已支付、未使用的订单**可申请退款；退款金额按「距演出开场时间」阶梯费率计算；接口幂等、并发安全、库存回补完整。

## 2. 业务规则

### 2.1 退款费率（时间锚点：演出开场时间）

| 距演出开场 | 手续费率 | 实退比例 |
|---|---|---|
| ≥ 7 天 | 0% | 100% |
| ≥ 3 天且 < 7 天 | 20% | 80% |
| ≥ 24 小时且 < 3 天 | 50% | 50% |
| < 24 小时 | 不可退 | — |

- 金额单位为**分**（BIGINT）；`refund_amount = pay_amount × 实退比例`，乘积向下取整；`手续费 = pay_amount - refund_amount`。
- 演出取消 / 延期的全额退款属于平台侧批量操作，**不在本设计内**。

### 2.2 可退条件（全部满足才可退）

1. `status = 2`（已支付）；
2. 未核销（`status = 3` 已使用不可退）；
3. 距演出开场时间 ≥ 24 小时。

## 3. 数据模型改动

`tb_ticket_order` 现状：`status` 注释已预留 5 退款中 / 6 已退款，`refund_time` 字段已有，**状态语义无需改**。

需要的改动：

| 改动 | 说明 |
|---|---|
| `tb_ticket_order.pay_amount BIGINT NOT NULL DEFAULT 0` | 实付金额（分），**下单时快照**，防演出改价后退款金额漂移；存量数据回填按 `tb_show.pay_value` |
| `tb_ticket_order.refund_amount BIGINT NULL` | 实退金额（分） |
| `tb_show.show_time DATETIME NULL` | **演出开场时间**，费率阶梯的时间锚点 |

⚠️ 时间字段辨析（易错点）：`tb_show_stock.begin_time` 是**开售时间**、`end_time` 是**停售时间**，都**不是**开场时间，不可混用。种子数据需为 10 场演出补 `show_time`。

### 状态机（v1）

```
2 已支付 ──申请退款──▶ 6 已退款（v1 同步完成，写 refund_time / refund_amount）
```

- `5 退款中` 保留给 v2 真实支付渠道的异步退款，**v1 不使用**；
- `4 已取消`（超时关单）与退款互斥——两者靠条件更新天然隔离（见 §6）。

## 4. 接口设计

统一 `Result` 包装；订单号是 18 位 ID，继续以**字符串**序列化返回（防前端精度丢失，同现有约定）。

### 4.1 退款试算　`POST /ticket-order/refund/preview/{orderId}`

供 AI 判定使用：**只算不退**。归属校验同 `queryOrderById`（非本人订单返回「订单不存在」，防遍历）。

可退时：

```json
{
  "code": 0,
  "data": {
    "orderId": "653386116245749764",
    "status": 2,
    "refundable": true,
    "showTime": "2026-11-20 19:30:00",
    "hoursBeforeShow": 72,
    "feeRate": 0.2,
    "payAmount": 48000,
    "refundAmount": 38400
  }
}
```

不可退时：`refundable: false` + `reason`（稳定文案，见 §7）。

### 4.2 执行退款　`POST /ticket-order/refund/{orderId}`

请求体可选：`{"reason": "个人原因"}`（仅记日志与客服追溯，不参与判定）。

```json
{
  "code": 0,
  "data": {
    "orderId": "653386116245749764",
    "status": 6,
    "payAmount": 48000,
    "refundAmount": 38400,
    "refundTime": "2026-11-13 15:20:00"
  }
}
```

### 4.3 查询

`GET /ticket-order/{id}` 现有接口已返回 `status` / `refundTime`，无需新增。

## 5. 执行退款的核心流程

1. **归属校验**：订单存在且属于当前用户（复用 `queryOrderById` 思路）。
2. **费率计算**：按 §2 算出 `refund_amount`（试算与执行必须走同一计算函数，保证 preview 与 execute 结果一致）。
3. **条件更新（幂等核心）**：`UPDATE tb_ticket_order SET status = 6, refund_time = now(), refund_amount = ? WHERE id = ? AND status = 2`——与超时关单 `cancelTimeoutOrder` 的 `where status = 1 → 4` 同款模板。**更新行数 = 0** 说明并发已处理：查当前状态，`6` 视为幂等成功返回，其余按对应拒绝文案处理。
4. **同事务回补 DB 库存**：`tb_show_stock.stock + 1`（与 `cancelTimeoutOrder` 的「DB 库存由调用方处理」约定一致）。
5. **事务提交后回补 Redis**（复用 `rollbackSeat` 语义）：`GRAB_STOCK_KEY + showId` 数量 +1；`TICKET_ORDER_KEY + showId` 移除该 userId（不移除则该用户永远抢不了这一场）。Redis 失败记 `error` 日志告警，策略与现有回补一致。
6. 日志前缀 `[退款]`，与 `[抢票]` `[关单]` `[下单]` 风格统一。

**幂等**：重复调用返回首次结果（`status = 6` 幂等成功），库存不重复回补。

## 6. 并发矩阵

| 并发场景 | 机制 | 结果 |
|---|---|---|
| 退款 vs 超时关单 | 关单只动 `status=1`，退款只动 `status=2` | 互斥，库存只回补一次 |
| 退款 vs 支付 | 支付只动 `status=1 → 2` | 互斥 |
| 双击 / 并发退款 | 条件更新 `2 → 6` 仅一次成功 | 幂等 |
| 退款后再抢票 | 限购占位已释放 | 允许，符合预期 |

## 7. 稳定文案（AI 侧依赖这些字符串做判定展示，勿随意改）

- 「订单不存在」（含非本人订单）
- 「订单未支付，无需退款」
- 「订单已使用，不可退款」
- 「订单已取消，不可退款」
- 「订单已退款，请勿重复申请」
- 「距开场不足 24 小时，不可退款」
- 「系统繁忙，请稍后重试」（Redis / MQ 异常兜底）

## 8. 验收清单

1. 已支付订单距开场 ≥ 7 天退款成功：`status=6`、`refund_time` 写入、DB 库存 +1、Redis 库存 +1、限购占位释放。
2. 费率边界正确：构造 7 天 / 3 天 / 24 小时三档边界订单，试算与实退金额符合 §2.1。
3. 幂等：同一订单连续两次退款，第二次幂等成功，库存只 +1 一次。
4. 拒绝路径：未支付、已使用、已取消、距开场 < 24h 四种情形文案符合 §7，状态不变、库存不动。
5. 归属校验：他人订单退款返回「订单不存在」。
6. 退款后同一用户可再次抢同一场演出。
7. 退款 vs 超时关单并发：状态终值唯一，库存最终一致。
8. 回归：抢票 / 支付 / 超时关单行为不变（跑现有 `TicketOrderFlowTests` 全绿）。

## 9. v1 边界（明确不做）

- 真实支付渠道对接（v1 视为即时到账的模拟退款）；
- 演出取消 / 延期的平台侧批量退款；
- 部分退款、退款审批流、优惠券 / 服务费扣除；
- 退款原因分类统计。
