# 压测实战复盘：从「数据很好看」到「找到真问题」

> 复现手册：`loadtest/README.md`（JMX 计划、token 造数、轮间复位；JTL/GC/JFR/报告等产物不入库）。本文是可复用的方法 + 面试可讲的版本。

## 1. 背景

抢票接口（Redis + Lua 预扣，MQ 异步落库）做完后，用 JMeter 对 `POST /ticket-order/grab/1`
做了六轮压测：500 个不同用户（直接写 Redis token 模拟登录）、50 张票。

## 2. 十轮实验总表

每轮只验证一个假设，改一个变量：

| 轮次 | 假设 | 实验 | 判定 |
| --- | --- | --- | --- |
| 1 | 建立基线 | Ramp-up 10s 稳态压 | P99 128ms、零错误、订单=库存 |
| 2 | 压力集中到 1s 会怎样 | Ramp-up 1s | 259 连接被拒、成功请求 P99 1858ms —— **发现异常** |
| 3 | JVM 扩堆触发长 GC？ | 固定堆 1G + GC 日志 | GC 最大停顿 29ms → **排除 GC** |
| 4 | 控制台日志串行化？ | 日志级别 debug→warn | 无改善 → **排除日志** |
| 5 | AMQP channel.open RPC 串行？ | channel 缓存 25→200，后做开/关 A/B | A/B 两侧均零被拒 → **归因未定**（轮间噪声主导） |
| 6 | 汇总复核 + 记录线程状态 | 同配置复跑 + 飞行记录 | 确认模式稳定（见第 4 节） |
| 7 | 默认 VM 配置复测 | 去掉固定堆/监控再跑一轮 | 132 被拒、456 req/s，落在前几轮的噪声带内 |
| 8-11 | channel 缓存 A/B + 复测 | 轮 8（开）/ 10（关）/ 11（开）各 500 并发 | **连续三轮零被拒**，吞吐 492~498、P99 492~606ms，随 JIT 预热变好 |

辅助实验：正确测量 Redis RTT（0.47ms、2117 ops/s），排除连接池排队；
RabbitMQ 管理台确认无内存/磁盘告警，排除流控。

## 3. 不变的结论（每轮都成立）

- 500 用户并发抢 50 张票：**订单数精确等于库存，零超卖、零重复**
- 每轮 50 笔订单 1 秒内异步落库，60 秒未支付全部自动取消、库存回补
- HTTP 层零 500、零超时（失败均为预期的业务拒绝或客户端连接问题）

## 4. 关键证据：时间分布分析（不需要高级工具）

对原始 jtl 做两个统计——被拒请求的**到达时间**、成功请求的**完成时间**：

**发现一：被拒的请求集中在洪峰开始阶段。**
轮 3/4 的被拒（73/197 个）全部落在开始后 **0 ~ 0.15 秒**；轮 7 的 132 个中 96 个落在前 0.2 秒、
其余散布全程。500 个 TCP 连接几乎同时到达，Tomcat 的 accept 队列（默认 100）被打满，
多出来的连接被操作系统直接拒绝。

**发现二：成功请求的完成时间全部堆积在最后。**

```
第三轮完成时间直方图（427 个成功请求）：
  0.1s ~ 1.1s 之间完成：0 个
  1.2s: 179 个    1.3s: 248 个
```

请求在 0.5 秒内全部到达，但**中间整整一秒没有任何一个完成**，最后 0.15 秒内一起返回。
「全部堆积到最后一起完成」说明存在全局性的排队/干扰，而不是随机的慢。

**发现三：服务端各组件实测都不慢。**

- Redis 往返实测 0.47ms（2117 ops/s），就算全部命令排队也只需 ~71ms
- GC 最大停顿 29ms
- RabbitMQ 无内存/磁盘告警

三个发现放在一起：服务端不慢、客户端（JMeter 500 线程）和被测系统挤在同一台笔记本上
互抢 CPU/调度——洪峰期客户端发请求、读响应都被调度延迟，被拒是 accept 队列瞬时打满。

## 5. 结论

1. 业务正确性在真实压力下完全成立：零超卖、零重复、延迟关单正常
2. 服务端各环节实测都健康，**瓶颈是「同机自压测」的测量方式本身**：
   客户端与被测系统互抢资源，洪峰期的数字被客户端因素污染
3. 单机自压测的数字**只能用于轮间对比，不能当后端绝对容量**；
   要测真实峰值，需要压测机与被测系统分机部署，并梯度加压找拐点

> 措辞建议：简历和面试里使用第一轮的稳态数字（P99 128ms、零错误）+ 「零超卖」，
> 不要引用洪峰轮的吞吐——那些数字被客户端因素污染了。

## 6. 面试叙事

**30 秒速记版**（只背这个）：

> 压测十轮，先建基线再打洪峰。业务正确性每轮都验证：500 个用户抢 50 张票，订单数
> 精确等于库存、零超卖零重复，60 秒未支付自动关单回补。性能上：稳态基线 P99 128ms；
> 把 500 个请求压到 1 秒内后，出现过连接被拒的异常，我逐个验证了 GC（最大停顿 29ms）、
> 控制台日志、AMQP channel、Redis 连接池（RTT 0.47ms）、MQ 流控五个假设并配合
> 时间分布分析与 JFR 录制定位——服务端各环节实测都很快，被拒来自同机自压测的
> 调度干扰与 accept 队列瞬时打满；复测三轮洪峰全部零被拒、吞吐约 490 req/s、
> P99 约 500ms。结论：业务与容量都达标，同机自测噪声大，绝对容量需分机部署再测。

**展开时准备三个细节**（每个 20 秒）：

1. **accept 队列**：500 个 SYN 同时到，backlog 默认 100，溢出的直接 RST；
   对应 Tomcat 的 `accept-count`，可调大但治标
2. **怎么模拟 500 个不同用户**：直接往 Redis 写 500 个登录 token（后端鉴权只认
   `show-ticket:login:token:{token}` 这个 Hash），不用真发 500 次验证码
3. **分清两种失败**：「票已售罄」是 HTTP 200 + 业务拒绝，不是系统错误；
   压测报告的 Error% 只统计了系统级失败

## 7. 常见追问与回答

| 追问 | 回答要点 |
| --- | --- |
| 为什么不分布式压测？ | 单机先验证正确性；测绝对容量前需要先排除测量系统自身的瓶颈——这次正好证明了同机互扰 |
| accept 队列怎么调？ | `server.tomcat.accept-count`（backlog）和 `threads.max`；调大只能缓解洪峰，根治靠限流/接入层 |
| 下一步怎么拿到真实峰值？ | 压测机分机部署，梯度加压（50→100→200 并发）记录吞吐/P99 曲线找拐点 |
| 为什么要造 500 个用户？ | 一人一票限购下，500 并发同用户只能成功 1 次；不同用户才能测出「50 张票被 50 个人抢走」 |
| 压测发现了什么可以改进的？ | ① 高并发下同步日志是全局锁，应改异步/文件 Appender；② accept 队列瞬时打满，洪峰场景应接入限流；③ 都记录在项目已知优化里 |

## 8. 附录：JFR（进阶工具，当时用过，可讲可不讲）

第六轮额外用 JVM 自带的飞行记录仪验证了线程状态，结论与时间分布一致。

**如果面试官问到，最低限度的答法**：

- JFR 是 JVM 内置的事件记录器，开销 <1%，生产可开
- 用法：`-XX:StartFlightRecording` 启动 → `jcmd <pid> JFR.dump` 导出 → `jfr view` 看视图
- 当时看的三类事件：慢 SocketRead（网络 IO）、JavaMonitorEnter（锁竞争）、GC 停顿
- 被追问内部原理答不上就坦诚：「当时按视图分析的，事件模型的细节没有深入」——
  它只是定位手段之一，没有它结论依然成立（见第 4 节的时间分布）
