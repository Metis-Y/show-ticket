# 订单号生成与消费幂等

> 简历一句话：基于 Redis 的时间戳 + 自增序列生成全局唯一订单号，消息消费按订单号幂等，扣库存与插订单同事务。

## 1. 订单号设计

`utils/RedisIdWorker.java`：

```
orderId = (当前秒 - 2022-01-01) << 32 | Redis 当日自增序列
自增 key = show-ticket:icr:order:yyyy:MM:dd
```

- 高位是时间戳（约 41 bit），低位是当天序列号（32 bit），单日可支持 42 亿单
- 按天分 key，Redis 单个 key 的计数压力小，也方便按天清理
- 生成的 ID 单调递增，写入 MySQL 时是顺序插入，减少 B+ 树页分裂

### 为什么不用其他方案

| 方案 | 问题 |
| --- | --- |
| UUID | 无序，字符串主键索引大，插入随机导致页分裂；不可读 |
| 数据库自增 | 暴露订单量；分库分表时改造麻烦；高并发下自增本身是写热点 |
| 雪花算法 | 需要管理 workerId（部署、回收），存在时钟回拨问题；本项目已有 Redis，复用成本更低 |
| Redis `INCR` 纯序列 | 纯数字递增暴露订单量；重启/迁移时序列管理麻烦 |

雪花算法并不是不好，而是**本项目没有多机房、没有 workerId 管理诉求，Redis 方案更简单**。如果去掉 Redis 依赖，雪花是首选。

## 2. 消费幂等

RabbitMQ 是 at-least-once，重复投递的原因包括：消费者处理完但 ack 丢失、网络抖动、重试机制。

`TicketOrderServiceImpl.createTicketOrder`：

```
1. 按 orderId 查询，已存在 → 直接返回（重复消费）
2. 扣减 DB 库存（乐观锁 stock = stock - 1 where stock > 0）
3. 插入订单（主键是入口生成的 orderId）
整个方法 @Transactional，任一步失败都回滚
```

**为什么订单号在入口生成**：如果消费端生成，同一条消息重投会生成两个不同订单号，查重失效。

**为什么用主键而不是业务唯一索引**：如果对 `(user_id, show_id)` 建唯一索引，用户取消订单后就永远不能再买同一场；一人一票由 Redis 的 Set 控制，取消时 `SREM` 释放，天然支持重新购买。这是设计取舍，不是遗漏。

## 3. 状态流转与并发控制

订单状态：`1 未支付 / 2 已支付 / 3 已使用 / 4 已取消 / 5 退款中 / 6 已退款`

支付和超时关单可能并发：

```sql
-- 支付
UPDATE tb_ticket_order SET status = 2 WHERE id = ? AND status = 1
-- 关单
UPDATE tb_ticket_order SET status = 4 WHERE id = ? AND status = 1
```

两条语句互斥，看影响行数决定谁生效；只有关单成功的那一次才回补库存，避免“支付成功后库存又被加回去”。

## 4. 防超卖

```sql
UPDATE tb_show_stock SET stock = stock - 1 WHERE show_id = ? AND stock > 0
```

- Redis 预扣是第一道闸门（挡掉绝大部分请求）
- DB 乐观锁是最终保证（即使 Redis 数据不一致也不会超卖）
- 影响行数为 0 说明库存不足或数据不一致，回补 Redis 并告警

## 5. 事务边界

- `createTicketOrder` 标注 `@Transactional(rollbackFor = Exception.class)`，由 MQ 消费者通过代理调用，事务生效
- 曾经的坑：在同类内部直接调用事务方法，事务不生效（Spring AOP 代理问题），后来改为由消费者调用 service 方法，避免自调用
- 避免在事务里做 Redis 操作后不回滚：Redis 不参与事务，回补逻辑放在异常分支显式处理

## 6. 面试追问

- Q：订单号重复了怎么办？→ 时间戳 + 自增的组合在单实例内不会重复；Redis 单点保证 INCR 原子；跨天由日期 key 区分。
- Q：Redis 挂了还能生成订单号吗？→ 不能，抢票直接失败。可用号段模式（每次取 1000 个号缓存本地）降级，本项目未做。
- Q：为什么要用 MySQL 主键而不是唯一索引做幂等？→ 主键是必须的，唯一索引会误伤“取消后重新购买”的场景；幂等键用主键，业务约束用状态机 + Redis。
- Q：消费者重试会不会重复扣库存？→ 不会：查重在最前，重复消息直接返回；即使并发重投，主键冲突会让后一个事务回滚。
- Q：为什么扣库存和插订单要在一个事务？→ 只成功一半会出现“扣了票没订单”或“有订单没扣票”；同一事务保证原子性。
